Longfellow ZK 在证明什么、为什么快

这一课的收获：从零开始弄懂 Longfellow ZK，最后能不看稿、用 2 分钟英文讲清它的「陈述 → 证明系统 → 为什么快 → 部署到哪」。面谈开场他们一定默认你懂这个。

0. ZK 的基本名词：谁提供什么、谁看得到什么

后面所有课都用这一节的名词。先记住一句话：prover 手里有秘密，verifier 手里只有公开信息；两人对着同一条公开规则，prover 要让 verifier 相信「我有一个满足规则的秘密」，又不把秘密交出去。

0.1 名词表

名词是什么谁提供谁看得到在 mdoc 年龄验证里是什么
关系 / 电路
relation R / circuit C		公开的检查规则：R(x, w) = 1 表示「w 是 x 的合格证据」。写成加法门、乘法门组成的电路，就是 C(x, w) 输出 1。协议设计者 / 标准（提前固定）双方「MSO 的哈希能被发证方公钥验签 + 披露的属性在 MSO 里 + 没过期 + device 签了本次会话」这一整套检查

0.2 三条安全性质（各自防谁）

性质意思防的是谁和 MPC 的对应
完备性 completenessx 为真、prover 诚实 → verifier 一定接受。（不防人，保证「能用」）正确性
可靠性 soundnessx 为假 → 作弊的 prover 几乎不可能让 verifier 接受。「几乎」的概率叫可靠性误差（soundness error），比如 2−128。恶意 prover（拿假驾照的人）恶意安全里「作弊会被抓」
零知识 zero-knowledgeverifier 除了「x 为真」这一个比特，学不到关于 w 的任何东西。好奇的 verifier（想追踪用户的网站）「只泄露输出」
两个容易混的词：proof vs argument、proof of knowledge
  • proof（证明）vs argument（论证）：proof 的可靠性对算力无限的 prover 也成立；argument 只对算力有限的 prover 成立（比如假设 prover 找不到哈希碰撞）。Ligero 和 Longfellow 严格说是 argument，但大家口头都说 proof。
  • proof of knowledge（知识证明）：不仅证明「存在合格的 w」，还证明「prover 确实知道 w」。证明「我持有一个合法签名」需要的是这一种 —— 对一个公钥，合法签名总是「存在」的，关键是你手里有。第 0003 课的「签名持有证明（proof of possession）」就是这个意思。

0.3 再补四个背景概念

  • 数字签名：输入（私钥, 消息）→ 签名；验证输入（公钥, 消息, 签名）→ 通过 / 不通过。
  • 哈希函数（如 SHA-256）：输入任意长数据 → 输出固定长度的「指纹」（摘要 digest）；找不到两份数据有相同指纹。签名通常签的是消息的摘要。
  • 有限域 GF(q)（GF = Galois Field，伽罗瓦域）：电路里的加和乘都在这里做，是「只有 q 个元素、能加减乘除的数系」。两种常见的：素数域 GF(p)（整数模 p，ECDSA 用这种）和二元域 GF(2k)（元素是 k bit 串，加法就是按位 XOR = exclusive OR 异或，适合 SHA-256 这种比特运算）。同一个计算放在对的域里，电路能小几十倍。
  • 透明 / 基于哈希 → 后量子：很多出名的 ZK 系统（如 Groth16）需要可信设置，而且依赖椭圆曲线配对，量子计算机能攻破。基于哈希（hash-based）的系统只假设哈希安全；量子计算机对哈希只有平方根加速（Grover 算法），加大参数即可 —— 所以被认为是后量子安全的。Longfellow 属于这一类。

1. Longfellow 整体：输入、输出、证明了什么

是什么
Google 的零知识证明库与协议（幻灯片里也叫 libZK），名字不是缩写。
Prover 输入
statement x（发证方公钥、要披露的属性、日期、会话信息）+ witness w（完整证件 MSO、发证方签名、device 公钥与 device 签名）
Prover 输出
一个证明 π
Verifier 输入
statement x + π
Verifier 输出
接受 / 拒绝
保证
接受 ⇔ 用户确实持有一张合法发证方签发、未过期、属于这台手机的证件，且披露的属性是真的；网站学不到其他任何东西

1.1 应用场景：手机证件 mdoc

手机里的数字驾照 / 身份证遵循 ISO/IEC 18013-5 标准（ISO = International Organization for Standardization 国际标准化组织，IEC = International Electrotechnical Commission 国际电工委员会；标准全名 Personal identification — ISO-compliant driving licence — Part 5: Mobile driving licence (mDL) application）。它定义的证件数据格式叫 mdoc（mobile document，手机证件），电子驾照 mDL（mobile Driving Licence）是 mdoc 的一种。三方角色：

  • 发证方（issuer）：比如州车管所，负责签名；
  • 持有人（holder）：用户和他们的手机 —— 在 ZK 里就是 prover；
  • 依赖方（relying party）：要查证件的网站、app、读卡器 —— 在 ZK 里就是 verifier。

发证方不参与 ZK 证明本身，它只是在很早以前签了证件；它的公钥是 statement 的一部分。

1.2 证件里有什么（witness 的来源）

发证方用 ECDSA P-256 签名。ECDSA = Elliptic Curve Digital Signature Algorithm（椭圆曲线数字签名算法）；P-256 是 NIST（National Institute of Standards and Technology，美国国家标准与技术研究院）在 FIPS 186（FIPS = Federal Information Processing Standard，联邦信息处理标准）里定义的一条曲线，也叫 secp256r1。

被签名的是 MSO（Mobile Security Object，移动安全对象），里面有：

  • 每个属性（age_over_18、姓名、生日……）的 SHA-256 摘要（SHA = Secure Hash Algorithm；SHA-256 是 SHA-2 家族中输出 256 bit 的版本，标准 FIPS 180-4）。MSO 只放摘要不放原文，这样出示时可以只交出部分属性的原文；
  • 用户手机的 device key（设备密钥）的公钥。私钥锁在手机安全芯片里，出示时用它签一下本次会话，证明「证件没被复制到别的设备」（叫 device binding 设备绑定）；
  • 有效期。

出处：CiC §6.2, Alg. 10（CiC = IACR Communications in Cryptology，Longfellow 论文正式发表的期刊；IACR = International Association for Cryptologic Research；Alg. = Algorithm）。

1.3 电路 R 检查的四件事

  1. MSO 的 SHA-256 摘要能被发证方公钥的 ECDSA 签名验证通过；
  2. 披露的属性（如 age ≥ 18）的摘要就在这个 MSO 里；
  3. 证件在有效期内；
  4. 本次会话被 MSO 里那个 device 公钥签过名 —— 而 device 公钥本身是隐藏的（在 witness 里）。

1.4 为什么非要 ZK？

不用 ZK 的原版 mdoc：每次出示都把 MSO、发证方签名和 device 公钥原样交给依赖方。这三样在每次出示中都一模一样，于是：

  • 两个网站对比收到的签名，就知道是同一个人（可链接 linkable）；
  • 发证方也见过这个签名："enables the issuer of the MDOC to collaborate with the relying party in order to identify users across sessions."CiC §6.2 车管所 + 网站一合谋，就知道某人何时登录了哪个网站。

ZK 把这些不变的东西全放进 witness，每次出示的 π 都是全新的随机串，因此不可链接。这类「可选择性披露、出示之间不可链接」的证件学术上叫匿名凭证（anonymous credentials） —— 论文标题 Anonymous credentials from ECDSA 的意思是：发证方的 ECDSA 基础设施一点不改，只在持有人这一侧加一个 ZK 证明。这是它能真正部署的根本原因。

要点：被证明的东西（statement 里的签名和哈希）是经典密码（ECDSA + SHA-256）；证明系统本身只依赖 SHA-256。这两层别混在一起，第 6 节和第 0004 课会用到。

2. 证明系统的两个积木（先看黑盒）

Longfellow 由两个现成的协议拼起来。先只看它们各自的输入输出，第 3 节再看怎么拼，第 0002 课用 MPC 视角拆开内部。

名字
sumcheck（求和校验协议，Lund–Fortnow–Karloff–Nisan 1990）＋ GKR 框架（Goldwasser–Kalai–Rothblum 2008，三位作者首字母）
输入
一张分层电路 C（公开）、prover 手里的 witness、一个声称「C 的输出是 y」
输出
一份交互记录（transcript）；verifier 读完后只剩一个关于输入层的小检查
负责
电路的「体力活」：把「整张电路算对了」逐层归约成「输入满足一个小等式」
优点
prover 时间与电路门数成线性，O(C)（C = 门数）—— 非常快
缺点
本身不是零知识（消息会泄露 witness 信息），也不能承诺 witness
名字
Ligero（Ames–Hazay–Ishai–Venkitasubramaniam，ACM CCS 2017，即 ACM Conference on Computer and Communications Security；西班牙语「轻」，不是缩写）
输入
prover：一串秘密数 + 一组关于它们的线性 / 二次等式；verifier：这组等式
输出
一个对这串数的承诺 + 一个零知识证明「承诺里的数满足这些等式」
负责
承诺 + 零知识；只用哈希，透明
缺点
等式越多越慢；直接用它证整张大电路代价高

一句话分工：sumcheck 快但不藏秘密；Ligero 藏秘密但怕大电路。Longfellow 让 sumcheck 处理大电路，Ligero 只处理很少的等式。

sumcheck 和 Ligero 内部大致怎么做到的
  • sumcheck：要让 verifier 相信「某个多元多项式在所有 0/1 输入上的和等于 S」。每一轮 prover 发一个一元多项式，verifier 检查一个简单等式并回一个随机数，一轮消掉一个变量；最后 verifier 只需在一个随机点算一次。GKR 把它在电路上逐层用：「第 j 层的值对」⇒「第 j+1 层的值对」⇒ …… ⇒ 输入层。
  • Ligero：基于 MPC-in-the-head —— prover 在自己脑子里模拟一个 MPC 协议的所有参与方，把每方的视图承诺起来，verifier 随机打开几方检查。具体实现是把数据做 RS 编码（Reed–Solomon，见第 4 节）排成矩阵，用哈希树（Merkle tree）承诺，verifier 随机打开若干列。这就是 IOP（Interactive Oracle Proof，交互式预言机证明：prover 给一大串数据，verifier 只抽查几处）。

3. 配方：怎么把两个积木拼起来

输入
prover：statement x + witness w；verifier：statement x
第 1 步
Ligero 承诺 witness w 和一串随机掩码 pad
第 2 步
跑 sumcheck，但每条消息都加上 pad 再发 → verifier 看到的是「加密的 transcript」
第 3 步
Ligero 证明「承诺里的 w 和 pad + 公开的加密消息，解密后能让 sumcheck verifier 接受」—— 只有约 d 个二次等式（d = 电路层数，通常 < 20）
输出
π = Ligero 承诺 + 加密 transcript + Ligero 证明

为什么这比「直接用 Ligero」快："Our formulation only requires Ligero to handle d quadratic constraints where d is the depth of the original circuit (typically a small integer < 20), whereas the original circuit may contain thousands of multiplications."CiC §2.3

零知识从哪来：verifier 只看到「消息 + 随机 pad」，等于看到随机数 —— 和 MPC 里用一次性掩码把在线消息变成均匀随机是同一种直觉。

他们自己的一句话版本（IETF 126 第 7 页幻灯片；IETF = Internet Engineering Task Force 互联网工程任务组，126 是会议编号，2026 年 7 月）：

"Follows the oldest ZK 'recipe' from BGGHKMR88. Run an IP → Transcript. Commit to Transcript → Com. ZK for 'Com contains T and IP-verifier(T)=1'. IP: Sumcheck. Commit/ZK: Ligero (IOP, only uses SHA256.)"IETF 126 slides

原文里的词意思
BGGHKMR88七位作者 Ben-Or, Goldreich, Goldwasser, Håstad, Kilian, Micali, Rogaway 的首字母 + 1988；论文 Everything Provable is Provable in Zero-Knowledge（CRYPTO 1988）。配方：先跑一个普通交互证明，但不明文发消息而是发承诺，最后用 ZK 证明「承诺里的消息能让 verifier 接受」。
IP → TranscriptIP = Interactive Proof（交互式证明）；跑完得到 transcript（所有消息）。这里的 IP 就是 sumcheck。
ComCommitment，承诺。
IP-verifier(T)=1「把 transcript T 交给 sumcheck 的 verifier，它会接受」。
IOP, only uses SHA256Ligero 是一个 IOP（Interactive Oracle Proof），落地时只用 SHA-256。

最后一步：Fiat–Shamir 变换（Fiat 与 Shamir 1986，两位作者的姓）。输入：一个交互协议；输出：一个非交互协议 —— 把 verifier 的随机挑战换成「对之前所有消息做哈希」。这样手机一次性生成 π，网站离线验证，不用来回通信。

4. 为什么快：每个子计算放在合适的域里

先看结论：电路分成两半，各用一个对它最便宜的域，中间用一个随机检查保证两半用的是同一份 witness。

子计算放在哪个域为什么代价
ECDSA P-256 验签P-256 自己的素数域 GF(p)，计算时借用二次扩域 GF(p2)不用模拟 256 bit 大数运算约 1.5×（以前的做法是 40–100×）
SHA-256二元域 GF(2128)，承诺时用子域 GF(216)SHA-256 全是比特运算，二元域里 XOR 是免费的加法每个承诺元素只占 16 bit
两半之间—随机 MAC（Message Authentication Code，消息认证码）检查两边是同一份 witness很小

CiC §1, §3.3

4.1 难点：P-256 的域不支持快速编码

组件
Reed–Solomon 编码（RS 码）—— Ligero 承诺时要用
输入
k 个域元素
输出
n 个域元素（n 比 k 大好几倍，Longfellow 用 7 倍）
性质
改动输入中任何一个数，输出里绝大多数位置都会变 → verifier 随机抽查几处就能抓住作弊
要快
需要 NTT（Number Theoretic Transform，数论变换 = 有限域上的 FFT，Fast Fourier Transform 快速傅里叶变换），把 O(n²) 降到 O(n log n)
NTT 前提
域里要有大阶单位根（存在 ω 使 ωn = 1，n 是 2 的大次幂）

问题：P-256 的素数域没有大阶单位根，NTT 做不了。Longfellow 的解法：在二次扩域 GF(p2) 里做 NTT（二次扩域就像从实数扩到复数，每个元素写成 a + b·i），那里有足够大的单位根，代价约 1.5×。

为什么 GF(p) 没有、GF(p²) 有

GF(p) 里有 2k 阶单位根，当且仅当 2k 整除 p − 1。P-256 的 p = 2256 − 2224 + 2192 + 296 − 1 是为椭圆曲线运算快而选的，p − 1 只含一个因子 2，所以只有 ±1。GF(p2) 的乘法群阶是 p2 − 1 = (p − 1)(p + 1)，而 p + 1 = 296 × 奇数，所以有 296 阶单位根。另外他们把 RS 的求值点选成等差数列 0, 1, 2, …，这样编码变成一次线性卷积，卷积再用扩域 NTT 算；数据本身仍在 GF(p) 里。

4.2 SHA-256 那一半换到二元域

SHA-256 全是 32 bit 字的 XOR、AND、循环移位、模 232 加法。素数域里每个 XOR 都要单独约束，很贵；二元域 GF(2128) 里 XOR 就是加法，免费。128 bit 是为了让可靠性误差到 2−128 量级。二元域的快速编码算法叫加性 FFT（additive FFT）。

4.3 两半之间的一致性检查

组件
跨域随机 MAC
输入
两个证明各自承诺的 witness 副本 + verifier 的随机密钥（在承诺之后才选）
输出
相等 / 不相等
保证
如果两边的 witness 不一样，MAC 碰巧相等的概率可以忽略 → prover 不能在两半各填一个不同的值

→ 这正是 Matteo Frigo 的老本行：他是 FFTW（Fastest Fourier Transform in the West，最常用的 C 语言 FFT 库，和 Steven G. Johnson 合写）的作者，凭它拿了 1999 年 J. H. Wilkinson 数值软件奖。聊到 NTT / 加性 FFT 时可以自然地提一句。

「quantum-safe」到底指什么？

他们的措辞是 "transparent, hash-based" 证明系统，"for proving statements about credentials signed with legacy algorithms (ECDSA, SHA-256)"，以及 "Deploying (new) ECC crypto in 2026 is not responsible."IETF 126 slides 4–5（ECC = Elliptic Curve Cryptography，椭圆曲线密码。）用第 0 节的名词拆成两层：

层现在用什么后量子吗
证明系统（prover / verifier 算法）只依赖 SHA-256是
statement 里被证明的签名发证方的 ECDSA不是：量子计算机上的 Shor 算法能从公钥算出私钥，任何人都能伪造证件

要让整条链后量子，发证方得改用 ML-DSA 这样的后量子签名，Longfellow 的电路就要能高效地检查「我持有一个 ML-DSA 签名」。→ 这正是你的切入点：你做过门限 ML-DSA（签发侧），他们 858 ms 的 ML-DSA 电路是持有人侧。

Longfellow lets a wallet prove it holds an mdoc credential — an ECDSA P-256 signature over a SHA-256 digest of the MSO — and reveal only one attribute, with the device key hidden so presentations can't be linked. The trick is the old recipe: run sumcheck over the layered circuit, commit to a padded transcript, and use Ligero to show the committed transcript makes the verifier accept, so Ligero only sees a handful of quadratic constraints. The P-256 half uses an NTT in a quadratic extension, and SHA-256 lives in GF(2^128). The proof system only assumes SHA-256, which is why it's a natural base for post-quantum credentials — the open part is the statement: the issuer signature has to become ML-DSA.

英文稿里的缩写可以照念：mdoc 念 "em-doc"，MSO 念 "M-S-O"，NTT 念 "N-T-T"，GF(2^128) 念 "G-F two to the one-twenty-eight" 或 "the binary field"。

自测

Q0. 在 mdoc 年龄验证里，发证方公钥属于哪一类？
网站必须知道「是哪个（或哪些）发证方」才有意义，所以发证方公钥是公开的 statement；device 公钥才是 witness（第 0.1 节）。
Q1. 一个零知识证明结束后，verifier 学到了什么？
零知识性：除了陈述为真，什么都不泄露（第 0.2 节）。如果泄露了哈希，那个哈希本身就能用来跨会话追踪。
Q2. mdoc 出示时，device 公钥为什么要藏在 witness 里？
Device 公钥每次都一样，公开就成了追踪标识符（CiC §5.3, §6.2）。
Q3. Longfellow 中 Ligero 实际要处理的约束大约有多少？
sumcheck 处理电路本身；Ligero 只证明「被承诺的 transcript 让 sumcheck verifier 接受」，约 d 个二次约束（CiC §2.3）。
Q4. P-256 那一半为什么不能直接做标准 NTT？
没有大阶单位根 → 在二次扩域 GF(p²) 里做 NTT，约 1.5× 开销（CiC §1）。
Q5. 2026-09 那篇 PQCA 博客说 Longfellow 是 "quantum-safe"，最准确的理解是？
博客没提 ML-DSA；IETF slide 用的是 "transparent, hash-based" 和 "legacy algorithms (ECDSA, SHA-256)"。
