2. 60 秒自我介绍

I'm a fourth-year PhD student at Virginia Tech with Thang Hoang. My main line is threshold post-quantum signatures: SHIELD, at S&P 2026, runs unmodified FIPS 204 ML-DSA signing inside maliciously secure MPC, so the output verifies under a standard verifier; FLOCK does the same for Falcon and is in the second round at USENIX Security. Along the way I reproduced the CCS threshold-Falcon artifact and found two silent bugs in its sampler and I/O layer — the fixes are merged upstream and signing got about nine times faster. I also work on ORAM. What pulled me to Longfellow is that it proves statements about unmodified standard signatures — the same philosophy as SHIELD — and the post-quantum version of that statement is exactly ML-DSA.

3. 三个项目提案（挑一个主推，另一个备着）

A. 隐藏公钥的 ML-DSA 签名持有证明（主推）

问题：device binding / issuer hiding 要求公钥隐藏，ExpandA 和 tr 必须进电路（ML-DSA-44 约 96 + 10 次额外 Keccak 置换）。现有测试电路假设公钥公开。
做什么：把 ExpandA（SHAKE128 拒绝采样）和 tr 放进电路；研究 Keccak 放在哪个域、怎么批量化、跨域连接怎么做最便宜；对比 858 ms 基线。
第一周：跑通 BM_MLDSA44ZK_Prove，按子电路（SHAKE、SampleInBall、NTT、UseHint、范围检查）做 profile，确认时间和证明大小花在哪。
成功标准：一个隐藏公钥的 ML-DSA-44 电路 + 一张成本拆解表 + 一份写给 CFRG / 论文的技术报告。
你的证据：Keccak / SampleInBall 的布尔电路你在 SHIELD 里做过；daBits 是跨域搬运的 MPC 版本。

B. 端到端后量子凭证：门限 ML-DSA 签发 + Longfellow 出示

问题：发证方改用 ML-DSA 后，签发私钥是单点；SHIELD 的输出是逐比特标准的 ML-DSA 签名，所以 holder 侧的 Longfellow 电路一行都不用改。
做什么：把 SHIELD 当 issuer 后端，签出 mdoc 风格的 MSO（ML-DSA 版），用 Longfellow 证明持有；量化整个管线的成本，找出 issuer 侧和 holder 侧各自的瓶颈。
第一周：定一个最小的 ML-DSA 版 MSO 格式；用 SHIELD 的 KAT 测试签出样例；接到 Longfellow 的 ML-DSA 测试电路上。
风险（主动说）：更偏系统集成；SHIELD 的离线预处理很重（摊销后每次成功签名是分钟级），适合低频签发，不适合高频。

C. ML-DSA 电路的规范一致性

问题：abhi 说 ECDSA 电路已证明与规范等价，ML-DSA 更难。
做什么：先做差分测试和对抗性测试（FIPS 204 KAT、边界情况：hint 的 ω 上限、z 的范数边界、SampleInBall 的上限）找实现层问题，再为形式化等价证明准备规范化的中间表示。
诚实的边界：你没写过 Lean；你的强项是在密码学 artifact 里找静默 bug。把它说成「我能在形式化之前把实现层的坑扫一遍，同时学 Lean」。

不要一上来就把三个都倒出去。先听他们说团队现在关心什么，再挑最贴的一个展开。A 是默认主推；如果他们更关心部署 / 发证侧，切 B；如果他们更关心形式化，切 C。

4. 要问他们的问题（挑 3–4 个）

  1. What does the post-quantum roadmap for Longfellow look like — is the next target issuer-side ML-DSA in mdoc, or device binding first?
  2. Your ML-DSA circuit is marked experimental. What would it take for it to become production-grade — performance, formal verification, or the spec side?
  3. How do you think about where Keccak should live — GF(2^128) with a cross-field link, or natively next to the F_q arithmetic?
  4. Is the Rust rewrite going to be the main code base going forward? Where would an intern's code land?
  5. For the internship itself: would this go through the PhD SWE intern pool I'm already in, or the Student Researcher track? Who would be the host?

7. 雷区

  • HERO 只说 untrusted helper，不提 SGX（投稿版没有 SGX）。
  • SHIELD 是「一个 CA 下的 n 台签名服务器，n-of-n，一次性可信 setup」—— 不是「多个 CA 联合签名」，不是 t-of-n，没有 DKG。
  • 不说「我测过 ZK 里的 ML-DSA 验签」；说「the same cost structure from the MPC side」。
  • 不说「两大 NIST 后量子签名标准」（还有 SLH-DSA；FIPS 206 未定稿），说「both lattice-based signatures NIST selected」。
  • 不贬低 Longfellow 的 ML-DSA 测试电路。
